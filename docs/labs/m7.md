## 7a: Commands and skills (about 9 minutes)

You reviewed a diff against a checklist in M5. Turn that into something you never retype.

1. **Feel the tax.** In a fresh session, type the review by hand, with the checklist, against `git show lab/m5-review`.
2. **Make a skill** at `.claude/skills/diff-review/SKILL.md`:
   - `name` (it becomes the slash command, so it must match the folder)
   - `description`: what it does **and when** to use it
   - `allowed-tools`: the tools it may use **without asking**. For a review, **read-only** tools only
   - a body that uses `$ARGUMENTS` for what you type after the command
   - the long checklist in a supporting file, `references/checklist.md`

   You may ask Claude Code to draft it. **Read what it pre-approved.**
3. **Run it:** `/diff-review lab/m5-review`.
4. **Flip a switch.** Add `disable-model-invocation: true`. What changes? When is that the right choice?

**Good to know:** a file at `.claude/commands/name.md` and a skill at `.claude/skills/name/SKILL.md` both create `/name`. Skills can also carry supporting files.

**Questions for your trio:** What did you pre-approve? Who reviews that line? Did Claude pick the skill up from a plain-English request?

## 7b: MCP

A small **read-only** MCP server for the local database lives in `tools/orders-db-mcp/`.

1. **Before you connect it**, read `tools/orders-db-mcp/README.md` and skim `server.mjs`. Write down: **What can it see? What could it change? What actually stops it?**
2. Add some data, then connect it:

   ```bash
   npm run dev                      # in a second terminal
   bash scripts/demo-data.sh        # adds a few orders
   claude mcp add --transport stdio orders-db -- node "$(pwd)/tools/orders-db-mcp/server.mjs"
   ```

   Start `claude` and run `/mcp` to see the server's status and tools.
3. Use it for a real question: *"Compare what the database says about stock and orders with what the code's rules say should be true. Is anything inconsistent?"*
4. Notice the permission prompts. Which calls would you auto-approve? Which never?

**Stretch:** The server can see customer emails. Change it so they **cannot be returned**, then try to defeat your own change. Is a check on the query text enough? Look at how the existing read-only guarantee is enforced, and why.

## 7c: Subagents (about 12 minutes)

1. **Build a read-only reviewer** at `.claude/agents/change-reviewer.md`:
   - `name` and `description` (what it does **and when** to use it) are required
   - `tools`: list **only** `Read, Grep, Glob`. **If you leave `tools` out, the subagent inherits every tool.**
   - the body is its system prompt: what to look for, to report **only what you can show with a file and line**, to say "none found" when that is true, and to end with what it could not check

   You may ask Claude Code to write it. **Check the `tools` line.** Then reload (restart the session, or use the agents command, depending on your version).
2. **Delegate:** *"Use the change-reviewer subagent to review `src/reporting/` and `src/orders/orders.service.ts` for correctness, security and requirement gaps."*
3. **Inline:** in a fresh session, ask the main session for the same review.
4. **Compare** the two:

   | | Subagent | Inline |
   |---|---|---|
   | Findings you can **confirm** in the code | | |
   | **False positives** | | |
   | File and line on each finding? | | |
   | Context used (`/context` before and after) | | |
   | Knew what you had discussed? | | |

A reviewer that is asked to find problems will usually report some. **Check each finding against the code.**

## 7e: Choosing the mechanism (about 6 minutes)

Mechanisms from this course: **instructions** (`CLAUDE.md`), **skills**, **subagents**, **MCP servers**, **hooks**, **permission rules**, **isolation or managed policy**, and the **repository's own tooling** (CI, linters, git hooks).

For each scenario, fill in a row. Do not debate yet.

| # | Scenario | Mechanism | Runner-up | What you lose with the runner-up | One limit or trust surface |
|---|---|---|---|---|---|
| 1 | The agent keeps writing tests that import `describe`, `it` and `expect` from the test library, but this project uses globals. | | | | |
| 2 | Every time a TypeScript file is edited, the type checker must run and the agent must see any errors. | | | | |
| 3 | At the end of each sprint, someone turns merged pull requests into release notes in the team's house format. | | | | |
| 4 | You need to find every place the code touches inventory reservation, which means reading dozens of files, without filling your working session. | | | | |
| 5 | Support wants to ask the agent about the current status of a customer's order, which lives in a database the agent can't see. | | | | |
| 6 | No one on the team, ever, may let the agent read local `.env` files or cloud credential files. | | | | |

**Ask in this order:** Must it happen every time, or should it? Do humans need the same rule? Then, what kind of thing is it?
